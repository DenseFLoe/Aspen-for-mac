# 静态验收要求

以 GitHub 主干 `main` 的[逆向成果目录](../逆向成果/)和[逐件总表](../逆向成果/逐件总表.csv)为准。接手者可以自行批量处理，每个原件都要有独立的验收结论和证据。

## 一件怎么验

1. **确认原件。** 从对象目录和总表找到原件、对应的逆向成果，以及已有的报告。核对产品、版本、原路径和原件 SHA-256（文件指纹）。同名文件要按指纹区分。逆向成果如果分成源码、资源、配置等多份文件，要一起检查。
2. **检查恢复得是否齐全。** 按原件列出应恢复的代码、成员和必要资源，再逐项核对交付。检查有没有漏失的实现、反编译失败或占位代码。原件中本来只有声明的方法，按原件证据记录。界面有控件、事件或数据绑定时，一起核对。
3. **检查逻辑是否对得上。** 对照原件里的分支、调用、计算和异常处理。`.NET` 文件可按方法清单核对，再用原件 IL（编译后的指令）比对恢复的代码。需要验证差异时，可重新编译恢复的源码，对照两边的方法实现、结构和资源。原生文件可用 Ghidra 检查函数、入口和必要的数据引用。遇到差异，要解释它的来源以及是否改变原逻辑。
4. **留下逐件证据。** 在对象目录保留或更新报告，每份成果配同目录的同名说明。记录原件与成果的路径和指纹、工具版本和操作、核对范围、证据位置、结论及待验证事项。确认失败时写明具体缺口、怎样复查，以及修好后要满足什么条件。证据应能定位到相应的方法、资源或文件。

原件身份已确认、应恢复内容齐全、关键逻辑有证据支持、影响整件的差异都已解决、成果和报告已归档，整件才算通过。编译成功只说明编译这一步通过。回编比较关注代码、结构和必要资源，整份编译产物的文件指纹可以因构建信息不同而变化。详细判定见[逐文件执行规则](reverse-execution-reference.md#31-完成判定)。

## 结果放哪里

| 当前目录 | 验收或复验结果 | 操作 |
| --- | --- | --- |
| [待静态验收](../逆向成果/待静态验收/) | 整件通过 | 将整个原件目录归入[静态验收通过](../逆向成果/静态验收通过/)，带上逐件证据。 |
| [待静态验收](../逆向成果/待静态验收/) | 已证实成果有缺口 | 将整个原件目录归入[静态验收未通过](../逆向成果/静态验收未通过/)，附错误报告。 |
| [待静态验收](../逆向成果/待静态验收/) | 原件无法取得、工具或依赖缺失，暂时无法判断 | 留在原目录，记录缺什么、恢复条件和已有证据。 |
| [静态验收未通过](../逆向成果/静态验收未通过/) | 按错误报告修复后通过复验 | 重做原失败检查，并按上面的整件标准核对修改涉及的内容。确认通过后，将修复成果、历史材料和复验证据一起归入[静态验收通过](../逆向成果/静态验收通过/)。 |
| [静态验收未通过](../逆向成果/静态验收未通过/) | 缺口仍在或还缺证据 | 留在原目录，更新错误报告和复验记录。 |

## 批量处理和提交

- 直接从主干的待验目录选件，从未通过目录和逐件报告取修复项。按 SHA-256 核对每件的状态，避免同件重复处理。
- 移动时保留产品、原相对路径和历史报告。在同一次提交更新目录、逐件记录、总表和受影响的索引。提交前检查新旧路径、证据和指纹。如果期间有别的批次合入，先按最新主干核对这一批仍需提交的变更。
- 通过 `codex/` 工作分支和 PR 合入主干。合入后从主干回读目录、总表状态和证据，再按[项目指令](../AGENTS.md)清理本次生成且已核验的本地副本。原件取用和公开归档遵循项目的资产保护与发布要求。

静态验收完成后，实际启动和使用的验证放在[Windows 重建对照阶段](development-requirements.md#3-先重建-windows-版并固定基准)。届时用相同输入和操作对照原版与重建版，核对正常结果、报错、保存重开及适用的数值结果。
