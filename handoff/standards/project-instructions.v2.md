# Aspen 项目指令

## 阅读方式

逐文件逆向任务默认只需本文件、[执行规则](docs/reverse-execution-workflow.md)和[当前状态](docs/reverse-work-status.md)。已在当前上下文中读取且未变化的内容不重复全文读取；上下文缺失、文件变化或结论存疑时重新核对。总纲、历史、清单和证据按任务定位相关章节/记录，不遍读全库。相关详细条款仍须执行，入口见[完整参考](docs/project-workflow-reference.md)。

## 现阶段核心工作

按[静态验收要求](docs/static-acceptance.md)从 GitHub 主干的待验目录批量选件，逐件对照原版。通过的归入静态验收通过目录，有明确缺口的归入静态验收未通过目录。按错误报告修复后，使用同一标准复验，再归档通过件。

## 不可省略的约束

- **资产永久保留、仅本地保存：** `.local/property-database/`（含 `plaintext-export/`、`archives/`、`DO_NOT_DELETE.md`）、`.local/formula-extraction-20261116/`、`.local/extraction-archives-20261117/` 中全部 `aspen-v15-formulas-*` 归档及校验/核验记录。保留原目录、元数据、恢复工具、公式图文与原始十进制数值；新增处理用新路径，禁止删除、清空、覆盖或损坏。只有用户针对具体路径明确授权才可例外。
- `.local/` 被忽略、已有压缩包或常规清理要求均不授权删除；禁止 `git clean -fdx`、`git clean -ffdx` 及递归清理整个 `.local/` 或 `.local/property-database/`。清理脚本明确排除保护路径。详见[数据库](docs/database-preservation.md)及[公式](docs/formula-extraction.md)。
- **范围：** Aspen Plus、独立的 Aspen Properties；Properties Enterprise Database Server 单列。各自原版安装包优先，已安装文件补缺、版本及运行证据；共享组件须有归属/依赖/调用证据。HYSYS、EDR、Energy Analyzer、Adsorption、Chromatography 等其他产品自身文件暂不调查或计入验收。
- **当前阶段：** 原版逐文件逆向归档。顺序为盘点 → 逆向归档 → Windows 重建及对照验收 → 从已验证基准复制独立 Mac 工程 → macOS 构建与实机复验。Windows 原源码保留，当前不自动启动重建。数值单位与容差在比较前确定。详见[总纲](docs/development-requirements.md)。
- **分类与完成分开：** Plus 既有分类冻结；Properties 五份清单为需要/不需要逆向、对应两份重复子集、尚未确定，类内按末级后缀排序。证据核实后才能确认分类，不能只凭后缀；内层代码单列。读取限制、路径定位和分类分别记录。双归属内容在双方及共用索引关联，同哈希共用 `analysis_key` 并保留来源，同名异哈希分开。历史清单与证据保留，新完成状态另建台账/视图。
- **每轮成果：** 验收通过放 `01-completed/`，局部、失败或未验收放 `02-incomplete/`；新归档保留产品、原路径/文件名，每份成果配同目录同名 `.md`，写来源/版本/哈希、范围、状态、验收证据、缺口和下一步。目录汇总、工具成功或编译成功不能替代逐文件完整性验收。
- **逆向工具：** 按实际格式选择。纯 .NET 延续 ILSpy 和 IL 核验。需要恢复的原生实现（含混合程序集的原生部分）优先用本机 `.local/reverse-tools/` 中的 Ghidra。Windows 对照阶段需要追踪原生运行行为时，使用同目录的 x64dbg 或 x32dbg。入口和用法见[执行规则](docs/reverse-execution-workflow.md#本机工具)。
- **子智能体：** 本类任务均允许按需调用，由模型决定数量及分工，无需逐轮确认；传递核心约束及必要上下文，分开写入路径，主智能体核验并统一同步完成状态。主模型可根据分派任务的难度，自行选择子智能体的模型和推理档位。
  - 逐文件逆向默认由 GPT‑6.2 Sol（High）主理。遇到回编差异、跨程序集绑定或新格式验收等影响整件判断的难点，优先将具体问题交给 GPT‑6.2 Astra（High）子智能体，主智能体负责复核证据并作出验收结论。
- **从下一轮起：** 同一来源成员不重复解包；多套代码对照、布局重复验证、深入追查外部依赖只为补具体缺口。行为测试留到 Windows 重建对照阶段。新归档只留正式成果、同名说明和必要证据；清单只验本轮增量。以往归档原样保留。

## 仓库工作流

- Aspen 本机目录按普通文件夹使用。此项目以后不初始化、克隆或创建本地 Git 工作树，不在本机维护 `.git` 或制作提交。需要从 GitHub 恢复可编辑文件时，从相应分支下载 ZIP 并解压到新目录。
- GitHub 公开仓库为 `https://github.com/DenseFLoe/Aspen-for-mac.git`。现有分支、默认分支和提交历史保留。后续发布走已认证的 GitHub 连接器，先读取目标分支的当前提交和适用指令，确认文件差异、范围、大小及适用检查，再直接在 GitHub 的 `codex/` 工作分支创建提交。不强推、不替换历史、不擅改默认分支。
- 逐件确认通过静态验收后，将完整源码、必要资源、同名说明和核验证据归档到 GitHub 主干 `逆向成果/静态验收通过/<产品>/<原相对路径>/`。按原件 SHA-256 查重，已有相同交付时在轮次索引 `reverse/01-completed/<轮次>/` 引用现有归档。提交前对照完成台账和成果指纹，回读主干确认后清理本次生成且已核验的本地副本。
- 工作表和 VBA 工程随文件自带的保护字段、仅用于该文件内部保护的口令、文件内的公式及必要的嵌入资源，均属于该件的交付内容，可随通过件完整公开。首次发布或补齐材料时沿用同一原件目录，并更新逐件说明和指纹表。
- 原版二进制和 `02-incomplete/` 中的逆向成果也可公开发布。静态验收修复 Issue 可提供原件、失败成果和错误报告，并记录路径与指纹。自编工具、项目文档和分类、来源、哈希、重复关系、定位及完成状态等元数据可上传。
- 上文列明的独立本地资产、真实账号及服务的认证凭据、安装包、工具安装包、缓存、构建产物和无关文件仅留本地。交付中混有这些材料时，逐文件核对发布范围并记录指纹。
- 每个已验证里程碑发布后核验 GitHub 分支、提交 SHA 和成果清单。连接器失败时保留本地普通文件，报告具体阻塞。

## 主分支分类目录

- 主分支按原件在 `逆向成果/` 中保存四种状态：静态验收通过、静态验收未通过、待静态验收、未成功。原件 SHA-256、产品及原路径用来区分同名文件；各来源版本和原报告保留在对象目录内。
- 发布包的内容指纹校验用于核对交付与解包。静态验收通过仍需原件级验收记录。`项目资料/` 收录工作计划、研究报告、工具与测试入口、沟通记录和原件清单。
