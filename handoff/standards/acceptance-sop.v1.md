# 验收操作流程标准 v1（派生摘要）

> **地位**：本文件是 [static-acceptance.v1.md](static-acceptance.v1.md)、[reverse-execution-workflow.v1.md](reverse-execution-workflow.v1.md)、[reverse-execution-reference.v1.md](reverse-execution-reference.v1.md) 的**派生摘要**，用于流水线照着执行。它**不具裁定力**；与上列原文或主干原文件冲突时，以原文为准，并以原文为准修正本文件。
> 依据版本：`main@f7959f39fd631692f14ecbbdfbf2496f543362b3`（2026-11-21）。

## 0. 总则

- 一件一结论、一件一证据。**目录汇总、工具成功、编译成功、已在他目录里**，都不能替代逐件验收。
- 判据只有一套：静态验收四步（P0–P3）+ 通过五条（P4）。不接受"这批都一样所以抽一个看"。
- 口径不清 → 不猜，标 `BLOCKED: standard_missing` 并指出缺哪一条。

## 1. 前置（每件开工前）

| 项 | 要求 | 出处 |
| --- | --- | --- |
| 原件身份 | 产品、原相对路径、版本、完整内容 SHA-256；同名文件按指纹区分 | static-acceptance §1；reference §3.1 |
| 来源 | 优先原版安装包，已安装文件补缺；记录包内成员与来源版本 | workflow §1 |
| 工具 | 纯 .NET：ILSpy + IL 核验；原生（含混合程序集原生部分）：Ghidra；运行期追踪留到 Windows 阶段用 x64dbg/x32dbg | AGENTS.md「逆向工具」 |
| 去重 | 同 SHA-256 + 同验收范围可复用已验收成果；跨批次按 SHA-256 对状态，避免重复处理 | static-acceptance「批量处理和提交」；workflow §1 |

## 2. 逐件四步（P0–P3）

**P0 确认原件**
从对象目录与逐件总表定位原件、已有成果、已有报告；核对产品 / 版本 / 原路径 / SHA-256。成果拆成源码、资源、配置等多份时，**全部一起查**。

**P1 恢复是否齐全**
- 列出"按原件结构应恢复"的代码、成员、必要资源，做**预期项 → 输出项**的覆盖记录。
- 托管件：核对类型与方法实现；按定义令牌（MethodDef）查漏，避免按名字漏项。
- 原生件：核对代码区域、函数、入口、必要数据引用。**导出伪代码/反汇编本身不算完整**。
- 界面：控件、事件、绑定一起核对。
- 原件中本就只有声明的方法：按原版证据记录，不误判为失败。

**P2 逻辑是否对得上**
- 对照分支、调用、计算、异常处理。
- .NET：方法清单 + **原件 IL 比对**；需要时回编恢复源码，比较两边方法实现、结构、资源。整包文件指纹可因构建信息变化，**不作为判定依据**。
- 原生：Ghidra 查函数、入口、数据引用。
- 有差异必须写清：**差异来源** + **是否改变原逻辑**。

**P3 留下逐件证据**
在对象目录保留/更新同名 `.md`，至少含：原件与成果的路径和指纹、工具版本与操作、核对范围、证据位置、结论、待验证事项；确认失败时写**具体缺口 + 怎么复查 + 修好后要满足什么条件**。证据要能定位到方法 / 资源 / 文件。

## 3. 通过判据（P4，五条全中才算通过）

1. **来源确定**：产品、路径、版本或不可取得原因、完整 SHA-256、与清单项的对应关系。
2. **覆盖完整**：类型/方法实现、原生代码区域与函数、必要资源都有预期-输出覆盖记录。
3. **缺口已处理**：没有未解释的缺失方法体、反编译失败、占位实现、无法推断的关键类型、未解析的内部成员。原版自身的抽象/接口/外部声明要有原版证据说明。
4. **证据可复查**：工具与版本、执行方式、日志、结构与实现核对证据、依赖边界，并区分**静态结论 / 原版运行观察 / 推断**。
5. **归档完整**：成果真实存在于 `01-completed/`，命名与路径正确，每份成果配同目录同名 `.md`，指纹与验收记录可核对。

> 只恢复局部类型或函数 ⇒ 整件**未完成**。编译成功 ⇒ 只说明编译这一步通过。

## 4. 三分支落点

| 结论 | 动作 | 出处 |
| --- | --- | --- |
| 整件通过 | 整个原件目录 `待静态验收/ → 静态验收通过/`，带上逐件证据 | static-acceptance「结果放哪里」 |
| 已证实有缺口 | 整个原件目录 `待静态验收/ → 静态验收未通过/`，附错误报告（缺口 + 复查方法 + 通过条件） | 同上 |
| 拿不到原件 / 缺工具依赖 | **留在原目录**，记录缺什么、恢复条件、已有证据 | 同上 |
| 修复后复验通过 | 重做原失败检查 + 按整件标准核对改动涉及内容，成果与复验证据一起归入 `静态验收通过/` | 同上 |
| 缺口仍在 | 留原目录，更新错误报告与复验记录 | 同上 |

**暂存 ≠ 完成**：需要新输入、新方法、新证据才能推进；同一失败条件下不机械重试（reference §4）。

## 5. 命名与归档

- 整份托管件：`<原文件全名>.cs`，配 `<原文件全名>.md`；局部输出：`<原文件全名>.<序号>.cs` 配同名 `.md`（如 `A.dll.cs`/`A.dll.md`、`A.dll.01.cs`/`A.dll.01.md`）。
- 原生 / IL / VBA / 资源材料保留原全名与能说明格式的后缀，**不把伪代码伪装成托管源码**。
- 保留产品、原相对路径、原文件名；异版本或异哈希用独立目录，不覆盖原版输入与历次成果。
- 每份成果都要有独立同名说明；目录汇总不能替代。

## 6. 提交与回读

1. 直接从主干 `待静态验收/` 选件，从 `静态验收未通过/` 按报告取修复项。
2. **同一次提交**更新：目录移动、逐件记录、逐件总表、受影响索引。
3. 合入前若主干有新批次，先按最新主干核对本批仍需提交的变更。
4. 走 `codex/` 工作分支 + PR；合并后**从主干回读**目录、总表状态与证据，再清理已核验的本地副本。

## 7. 公开与保留边界

- **可公开**：原版二进制、`02-incomplete/` 逆向成果、静态验收修复 Issue 中的原件 / 失败成果 / 错误报告（需带路径与指纹）。
- **仅本地**：安装包、数据库、公式、凭据、工具安装包、缓存、构建产物、无关文件；**含凭据的源码仅本地留存**（例：`SetupAPEDPostgreSQLDatabases.dll` 完整源码）。
- 不得输出秘密，不把凭据写入 URL 或日志。

## 8. 我方（执行方）附加约束

以下是**我方内部约束**，不是上游标准；列在此处只为让对方能核对我方交付是否自洽：

- 每件给**三档证据**：已实测 / 未验证 / 无法判定，不得混写。
- 每件回执固定字段：`sha256 / report path / dumps asset+member / analysis_key / 差在哪`。
- 产出只走 PR；正文只说这批改了什么、证据在哪、合并风险是什么。
- 无法判定时输出 `BLOCKED: <原因>`，不产出"看起来通过"的结论。
