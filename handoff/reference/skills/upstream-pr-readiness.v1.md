# upstream-pr-readiness —— 提 PR 之前先过六道闸门

权威来源：`skills\README.md` §4（内容条款）、§5（治理）；`skills\supervision-gates\SKILL.md`（门禁判绿）。
证据底本：`skills\upstream-pr-readiness\references\rejection-cases-20261102.md`（9 条驳回原文摘要，等级 A/B）。

> 目标不清（不知道提给谁、issue 什么状态、有没有人在做）先按 `skills\README.md` §4 第 10 条问一次，最多两轮；
> 被派出的子 agent 不向人提问，把缺项回给它调用的主 agent。
>
> 立标依据：2026-11-02 向 `T-Auto/dsh-ops` 同批提交 9 个 PR，维护者集中给出 `REQUEST_CHANGES`：
> **7 条建议关闭、2 条保留**（#566 修 4 点后可合并；#570 只有「双文件 per-file revision」一段被要求移植）。
> 驳回原因三类：**与既有在办工作重复（7 条）**、**方案含实现级缺陷（3 条：#565/#567/#571）**、
> **正文或证据与事实不符（多条）**。三类会叠加，一条 PR 可以既重复又含实现缺陷。

## 0. 何时用 / 不用

**用**：向上游（开源仓库、同事的仓库、任何你不拥有合并权的地方）提 PR 之前；PR 被驳回后决定「返工还是撤」；
判断一批 PR 该不该同时提。**不用**：自己仓库里怎么改都行；只想搞清某段代码怎么工作（走 `reverse-engineering`）。

与库内相邻技能的分工（技能库扩到 85 条后补，别混用）：正文排版与示例走 `pr`；issue/外部 PR 的状态机式
分诊走 `triage`；改动本身写得好不好（Standards/Spec）走 `code-review`；门禁判绿走 `supervision-gates`。
本文只管「该不该提、能不能过审、证据是否自证、驳回后返工还是撤」。

## 1. 六道闸门（顺序执行，前一道不过就停在原地）

### G0 重复度 —— 这个活现在有人在做吗（本次 7 条撞在这里）

1. issue **当前状态**仍是 `open` 吗？已 closed 的事，`Closes #N` 是硬错。
2. **同一批文件上有哪些 open PR**。GitHub 没有「按路径搜 PR」，先拉全量再本地求交：
   `gh pr list --state open --json number,title,files --limit 100 > prs.json`，再用 `node -e` 把
   `files[].path` 与你要改的路径求交；没有 `gh` 就 `GET /pulls?state=open` + `GET /pulls/<n>/files`。
3. issue **评论区**里有没有人认领（认领常在正文之后很久才出现）。
4. 维护者自己的 `work/<topic>`、`release/<x>` 分支上有没有相关提交。

写出 `DEDUP:` 行（怎么搜的、命中哪些 open PR、结论"无人做/应由 #x 承接"）。写不出就不要写代码。

### G1 可达性 —— 缺陷在**发布路径**上真的走得到吗

代码里有这段 ≠ 用户会走到这段。① 从真实入口追：组件/模块在默认配置里被挂载了吗？② 区分 **live** 与
**legacy-only**（被 `retiredXxxRow()`、`LEGACY_ROWS=1` 等开关挡住的对当前发行版不可达）。③ 只在受支持
版本上复现；已 EOL 的版本只谈维护分支。写 `REACH:` 行（入口 `文件:行`、默认可达与否、是否 legacy-only）。

### G2 契约 —— 我的方案会不会和在办 PR 互斥

同一 issue 的两种修法可能**语义相反**。这里的「断言」指三类可核对载体：**测试断言、schema/参数字面量、
文档里写死的字面量**。读在办 PR 的 diff，三类各扫一遍；只要它钉住了你想改的那个值就不能动
（例：一方要求 `expectedRevision` 必填并在文档写死 `"absent"`，另一方让它可省略）。
写 `CONTRACT:` 行（在办 PR #x 钉住 A、本 PR 要改 B、是否互斥）。

### G3 断言 —— 可证伪，且不许把"跑不了"算成"通过"

① 每条新行为都要有"撤掉实现就变红"的断言，并**真的跑一遍红→绿**。② **不得自相矛盾**：一条结果里不能
同时说"副作用未知"和"没有命令运行"。③ 环境受限时走**具名** `fixture unavailable: <reason>` 并**不计入
pass**，或直接失败。④ **跨平台不得静默通过**：`report()`/`process.exit()` 写在 `if (platform === 'win32')`
里等于别的平台"零检查 = 通过"；新套件同时要进门禁的平台 allow-skip 白名单。
写 `ASSERT:` 行（撤掉哪一行会红、受限时是具名 skip 还是失败）。

### G4 证据 —— 正文每个数字都能被一条命令复现

审查者会逐条重跑。本次被抓到的全是"引用与实测对不上"：过滤器命中 0 个套件仍计入总数；"三处 digest"
实为两处且都在同一文件；把断言值当字节测量；正文写的 skip 条件与代码不符。
`MEASURE:` 行——字节/token 用工具算（如 `js-tiktoken` cl100k_base）；"N 处/全部"要能被 `grep -c` 复核。

### G5 文案 —— 不得与代码或事实冲突

① `Closes #N` 的关闭理由必须**现在时仍成立**；issue 已因别的原因关闭就改 `Related to #N`。② 不要把
legacy-only 行为写成发布行为。③ 删除既有行为（哪怕是 bug）必须在正文声明"行为变化及理由"。④ **不要
把"部分改善"写成"消除了歧义"**——本次 #566 就栽在这句上（判据写清了，但常驻 reader 仍可能被读成覆盖该格式）。

## 2. 平台语义清单（本次 5 类缺陷全部源于"用 POSIX 直觉写 Windows 代码"）

| 语义 | 事实 |
|---|---|
| 文件模式 | `mkdir(…, { mode: 0o700 })` 在 Windows 被忽略；实测 `0o666` + 全继承授权 ⇒ 不能拿 mode 当私有性证据 |
| 路径同一性 | 全大写 / 正斜杠 / 8.3 短名 / `\\?\` 前缀四类拼写绕过字符串比较；只有 `fs.realpathSync.native` 能覆盖 |
| 环境变量 | POSIX 大小写敏感；Electron 类是"变量存在即生效"，不是 `=== '1'` |
| 安全描述符 | `CREATOR OWNER` 传播后会变成 owner SID；NULL DACL 父目录会让部分库 **panic 而非返回错误** |
| 句柄共享 | `FILE_SHARE_WRITE` 在"扩权后到发布前"的窗口里是可写入口 |

原则：凡涉及路径、权限、编码、时间、大小写、换行，先写一张本平台语义小表，再写实现。

## 3. 批量纪律

① **一次 1–2 条**。同批 9 条的代价：每条都被逐行审，任何一条硬伤拉低整批可信度；7 条要关闭时维护者得
连写 7 段驳回。② 优先选**唯一增量**——本次唯一被保留的 #566，理由不是写得好，而是"别人没在做"。
③ 同文件、同契约、同 issue 的两条不要同批提。

## 4. 收到 REQUEST_CHANGES 之后

① 先分类：`重复` / `不可达` / `契约互斥` / `实现缺陷` / `证据错误` / `文案错误`。前两类不值得返工——
关闭并写"采纳 #x"比重开一轮更专业。② 不在驳回理由上辩论，除非能给出反证实验；审查者本次每条都跑了实验。
③ **拆走残余价值**：唯一有价值的用例/校验规则单独 rebase 到承接 PR，而不是整条保留。④ 关闭要主动：
逐条关闭 + 一句承接说明，别占评审注意力。

## 4.1 提交前必须跑「交叉循环检验」，零阻断才允许提交

**硬门禁**：至少 2 名验证者，**互不知情**、**角度互补**（证据/主张 vs 环境/复现）、**只读**被测分支；
任一方的阻断项修掉后，由**同一批验证者重跑同一份清单**，直到双方零阻断；最多 3 轮，仍阻断则交人，
不许把阻断降级成"reviewer note"。未收敛不得提交。

结论只准三档：`已实测（命令+输出）` / `未验证（只读推理）` / `无法判定（缺什么）`。
PR body 的 Validation 段末尾必须附三行收敛记录：`LOOP: round <n> · verifier A <零阻断/阻断 k> · verifier B <零阻断/阻断 k> · 收敛 <是/否>`、
`FIXED: <本轮修掉的阻断项，逐条 file:line>`、`KNOWN: <仍无法判定的项 + 缺什么才能判>`。

落地细则（选角度、临时副本做变异、本机探针与临时根、**技能驱动的四轴分工**：A=`code-review` Standards、
B=`code-review`+`tdd`、C=`pr`+`writing-for-agents`、D=`diagnosing-bugs` Phase 1）读 `references\cross-verification-loop.md`。

## 5. 提交前检查表（逐项填，填不出就别提）
```text
DEDUP:    怎么搜的；命中 open PR <#…>；issue 状态 <open/closed>；结论 <无人做 / 由 #x 承接>
REACH:    入口 <文件:行>；默认安装可达 <是/否>；legacy-only <是/否>
CONTRACT: 在办 PR #x 钉住 <A>（测试/schema/文档哪一类）；本 PR 要改 <B>；互斥 <是/否>
ASSERT:   撤掉 <文件:行> → <套件> 变红（红/绿都已跑）；受限时 <具名 skip / 失败>
MEASURE:  字节 <+N>（命令）；token <+N>（js-tiktoken cl100k_base）
REPRO:    每个数字的来源命令已粘贴原样输出
PLATFORM: 路径 <realpath>；模式 <不依赖 mode>；环境变量 <大小写/存在性>；句柄 <共享位>
DOCS:     双语文档已同步；CHANGELOG 已加或写明不需要；legacy 行为未被写成发布行为
SIZE:     ≤1000 行/文件；≤~1000 行实现/PR；只碰 issue 点名文件；`git diff --check` 干净
BATCH:    本批 ≤2 条；与同批其它 PR 无文件/契约/issue 重叠
```

## 6. Gotchas

- **"改对了"不是充分条件**：7 条驳回里 6 条没走到实现质量（选题重复/不可达），另有 3 条确含实现缺陷。
- **维护者会跑你正文里的每个反例**：写"没跑过"比写一个能被推翻的断言安全。
- **issue 关闭速度可能快过你的开发速度**：开工前查状态，收尾再查一次。
- **环境 workaround 会污染证据**：为跑绿改 TEMP／修 `whoami` 之类不能进入通过判据，否则审查者一跑就红。
- **不要用"我知道哪里改了"代替"我核对过"**：本次"三处 digest"实为两处就是这类。
- **分支基线不要漂到 release 分支**：把 PR 分支 rebase 到 `release/x` 会让 diff 夹带发布提交（实测 6→19
  文件），正文的"文件数/base"立刻失真；PR 分支只跟它的目标分支。

## 7. 边界、来源与维护

- 样本：**一个仓库、一个维护者、一批 9 条 PR**（2026-11-02 快照）。换仓库/换维护者，「偏好」类判断
  （尤其对 legacy 代码的容忍度）可能不同；只有 G0/G3/G4 这类结构判据与工具无关。
- 未覆盖：安全类 PR 的威胁模型审查、性能类 PR 的基准口径、破坏性变更的迁移路径——本次都没提交。
- **没有**做过「按本清单改了之后是否真被合并」的前瞻验证（#566 仍在等复核），所以"按本清单做就能合"
  不在本文件的承诺范围内。
- G0 的求交命令只在 GitHub REST 下验证过；别的托管平台要改写（本机无 `gh` 时用 REST 等价写法）。
- 新案例往 `references\rejection-cases-20261102.md` 末尾追加，标日期与等级（A/B，分级见 `skills\README.md` §4 第 7 条）；
  维护者回复与仓库原文属 A/B，二手转述只能当线索；目标仓库的 `CONTRIBUTING` 优先，冲突取其原文。
