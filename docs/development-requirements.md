# Aspen for Mac 开发要求与实施顺序

## 开发总原则

2026-11-18 范围更新：**本次开发包括 Aspen Plus 与独立的 Aspen Properties。** 此要求覆盖盘点、分类调查、逐文件逆向、Windows 重建和 Mac 适配。两者各自的原版安装包为首选来源，已安装文件用于补充缺项、版本差异与运行证据。Aspen Properties Enterprise Database Server 作为 Properties 配套组件单列，不混淆其与主安装包的统计。共享组件按安装归属、依赖或调用证据纳入相关部分。

本轮任务边界：只新增 Properties 的第 1 步及分类复核。Plus 使用既有分类作为只读基线，只补共用文件交叉索引，不重新分类或新增本轮待核实统计。Properties 中与该基线同哈希的内容直接复用分类与分析记录；剩余新内容再核验。

分别维护 Plus、Properties、两者共用文件三份分类文档清单。双归属文件在三份清单同时列出；同哈希共用分析键并保留各来源，同名异哈希分别记录。两大类继续使用“需要逆向 / 不需要逆向”，类内按末级后缀排序；不得与已完成 / 未完成的成果验收分类混用。共用内容与同安装目标的版本差异分别登记，不能仅凭文件名或目录名判定共享。详细入口见[双产品盘点](plus-properties-inventory.md)、[Plus 清单](aspen-plus-classification.md)、[Properties 清单](aspen-properties-classification.md)和[共用文件清单](plus-properties-shared-files.md)。

HYSYS、EDR、Energy Analyzer、Adsorption、Chromatography 等其他产品自身文件仍不评估，不计入双产品的未分类项、未完成项和验收分母。全来源历史扫描继续保留并单列范围外记录；扩大产品范围须由用户明确提出。

以 Aspen Plus / Aspen Properties V15 安装介质和本机安装为参照。**先逐文件整理原版资料，再重建可编译的 Windows 版。Windows 基准通过验收后，复制出独立 Mac 源码，在副本里适配。** 本轮为新增 Properties 执行第 1 步及处理路线分类，项目总体第 2 步的原版反编译归档范围保持；本轮不启动重建。

### 1. 盘点安装包和已安装程序

解包安装介质，分别建立安装介质和本机安装文件的清单。每项记录来源、原相对路径、大小、类型、SHA-256 和可读取的版本。安装包中的文件还要记录所属安装组件和压缩包内的路径，便于追溯。用解包后单个文件的哈希与已安装文件比对。字节一致的文件共用一份分析记录，保留两边的路径。同名但哈希不同的文件分别记录。安装器文件、未安装的选件和安装后新增的配置也各自登记。

2026-11-18 来源选择：后续逐文件开发**优先读取 Aspen Plus / Aspen Properties 各自原版安装包中的载荷**；本机已安装的相关产品及共享目录只作为缺失文件、版本差异和运行观察的备选补充，不作为首选待反编译或待编译文件来源。扫描清单先分为“需要逆向”和“不需要逆向”，两类内部按末级后缀名（不区分大小写）排序；未知二进制保守列入逆向类并标明待核实。安装容器、资源、数据库与可读源码分别记录处理方式，不能因容器本身不需要反编译而漏掉内部程序。范围、统计与本地清单入口见[安装程序优先扫描](installer-first-inventory.md)。本次选择与扫描不启动 Windows 或 Mac 重建。

2026-11-18 分类复核：按后缀抽取不同内容样本，首选来源的 389 条原待核实记录覆盖全部内容哈希，其他来源按后缀补样。同一后缀可能同时包含实现、导入声明、资源或数据，不据后缀统一改类。只将实际检查过的内容哈希及明确的数据库元数据结论写入新清单，保留原清单、原来源和未完成的格式/逻辑工作。最新入口、核验和范围见[后缀抽样分类复核](suffix-sample-classification.md)。

2026-11-18 Properties 分类证据纠正：通用后缀/文件头规则仅作为初分，不等于内容分类验收；须保留待复核状态。内嵌 VBA 等代码成员单独核验，读取不可得与目标路径未解析分别登记。沿用既有 Plus 分类并排除相同哈希内容后，当前 Properties 新内容有 613 条首选来源记录待复核，已纠正 Properties 的 3 个 VBA 项目；上轮擅自扩大到 Plus 的重分类和待核实统计已撤出本轮交付。见[Properties 分类不确定项](classification-uncertainties.md)。

#### 1.1 每轮成果分类与逐文件说明

此子要求适用于后续各步骤。每轮反编译或编译结束后，按当轮验收结果，将成果文件分别归入以下两个目录，并保留原相对路径和文件名：

- **第一个目录 `01-completed/`（已完成）：** 存放工作完整完成且通过该阶段验收的文件。第 2 步以原版文件证据和反编译完整性为依据；后续编译与行为验证按各自阶段验收。
- **第二个目录 `02-incomplete/`（未完成）：** 存放尚未完成、仅部分恢复、编译失败或尚未通过该阶段验收的文件，并明确标注未完成原因。
- **两类目录均实行“一文件一说明”：** 每个成果文件须在同一目录配套独立的同名 `.md` 说明文件，例如 `A.dll.cs` 对应 `A.dll.md`，`A.dll.01.cs` 对应 `A.dll.01.md`。说明至少记录原版来源、文件版本与 SHA-256、本轮处理范围、完成状态、验收依据及证据位置、剩余缺口和下一步工作；不适用的字段注明原因。

目录级 `README.md` 或汇总表只能作为索引，不能替代逐文件说明。仅生成输出或编译成功，不能据此认定内容完整或通过该阶段验收。每轮归档使用新路径，保留此前成果、说明与验收记录；状态变化时在新一轮记录中注明依据。反编译资料继续仅本地保存，并遵守数据库与公式资产的永久保留要求。

### 2. 逐个反编译并按原名归档

2026-11-18 起，当前工作回到逐文件反编译与归档。对每份 C# 记录原版文件路径、版本和 SHA-256。整份托管代码完成件用「原文件全名.cs」，局部输出用「原文件全名.序号.cs」，保留安装产品和原相对目录。完成件与未完成件分开存放，均按第 1.1 项在同目录配套独立的同名 `.md` 说明文件，逐项记录验收依据和剩余缺口。来源无法确认为直接反编译的 45 个 Qt 工程文件已从整理分支移除，Windows 和 Mac 应用构建暂停。下文整合与构建记录对应此前的 Qt 工程。 [本地归档入口说明](step-2-source-attribution.md#当前源码归档)

逐个识别 `.exe`、`.dll` 等程序文件的类型。对 .NET 程序导出反编译结果，对原生程序保留可取得的反汇编、伪代码和依赖记录。无法读取或只能部分恢复的文件也登记原因。反编译结果按来源版本、原相对路径和文件名保存在本地。同名异版的输出用版本和哈希区分。资源、配置和数据库按各自格式解析，并记录可追溯的来源。数据库资产的新增导出使用新路径，遵循[数据库永久保留原则](database-preservation.md)。

每个文件记录使用的工具与版本、已确认的用途、入口和依赖、对应的证据位置与待核实项。追踪跨文件调用时，核对谁调用谁、输入输出的数据含义和单位、默认值及失败行为。关键推断用原版运行核实，并标记证据来自静态分析、原版观察还是待验证推断。反编译结果和原版依赖文件归入本地研究资料，供重建源码回查。

现有源码的功能段、原版文件定位及待核实事项见[第 2 步源码对照表](step-2-source-attribution.md)。每条记录按已有证据明确计入范围。

### 3. 先重建 Windows 版并固定基准

按已确认的行为编写可编辑的 Windows 工程。接通模块调用，配齐依赖库、配置、资源和构建文件。记录编译器、依赖版本、目标架构及构建和测试命令，在干净的 Windows 构建目录中复现编译和运行。

用原版 Windows Aspen 和 Windows 重建版运行同一批案例，记录原版版本、输入与单位、操作和可观察的结果。覆盖正常、边界及失败场景，包括项目保存重开、错误反馈及适用的数值输出。先确定比较指标和容差，再做计算对照。用提交号固定通过验收的 Windows 源码，同时保留构建配置、依赖清单、测试案例和对照结果。

### 4. 从 Windows 基准复制独立的 Mac 源码

原样保留已验收的 Windows 源码和基准记录。从对应提交复制出独立的 Mac 工程，记录复制所用的 Windows 提交。两套源码分别维护和构建。扫描与替换只发生在 Mac 副本里。

检查源码中的 Windows 系统调用、第三方库、文件路径和编码假设，以及构建和打包配置。为确有平台依赖的地方选用 macOS 支持的接口或库，调整引入资源及打包的方式。记录替换前后的依赖、涉及文件和需要复测的功能。复制来的业务逻辑按 Windows 基准的案例逐项复测。

### 5. 在 Mac 上编译并实机验收

记录目标 macOS 版本、CPU 架构、编译工具和依赖版本，在干净环境中构建应用并核对打包后的运行依赖。在 Mac 实机上启动应用，按 Windows 基准的案例复跑，核对文件选择、数据库访问、打开、保存和重开，以及适用的数值输出和失败行为。

分别记录自动构建、包内测试、实机运行和功能对照的结果。每次验收附源码提交、使用的案例、输入、容差及未通过项。需要分发时，签名、公证和安装体验单独验收。

## 项目模型与字段约束

1. 对象使用稳定标识建立关系，显示名称可以修改。页面控件负责编辑和展示，项目模型负责持有业务数据；保存和求解均从项目模型读取。
2. 区分业务输入、界面显示状态和计算结果。输入至少表达数值、单位或量纲、是否已指定及必要的对象引用；不得把空值、缺失值和数值零混为一类。
3. 保留尚未接入语义的会话输入，明确其未验证状态，避免迁移到项目模型时丢失现有输入。按首批案例逐页接入，不以一次性恢复全部变量绑定作为前置条件。
4. 项目文件包含格式版本和数据依赖标识。写入应使用临时文件及成功后的替换机制；读取失败不得破坏当前项目，未来格式迁移需保留可恢复的原文件。
5. 基础撤销重做至少覆盖对象创建、重命名、删除、输入修改和图形移动；新增连接编辑功能时同步纳入撤销范围。界面、导航、对象列表和模型状态必须一致。

## 数据接入与永久保留

[数据库永久保留原则](database-preservation.md) 和 [AGENTS.md](../AGENTS.md) 对所有阶段持续生效。受保护的原始导出、归档、校验记录和保留声明不得因开发、恢复、构建或清理而删除、覆盖或损坏。

- 运行用数据库、索引及迁移结果一律写入新的本地路径；应用只读访问已发布的数据版本。运行数据与原始资产分离，数据库内容及归档不加入 Git、不上传 GitHub。
- 参数身份保留数据库、子库、组分实体、物性与元素顺序；不得仅按显示名称合并记录。查询展示与可用于计算的参数分别标明验证状态。
- 原始 `value_text` 十进制字符串、单位、来源和关系元数据完整保留。数值预览、API 数组或转换后的计算值不得覆盖原始表示。
- 当前有 52,611 条 API 数组表示差异需要按物性类别解释。先验证首批计算需要的参数子集；组分检索无需等待全部差异解决。未解释的差异不得自动修正、补零或直接投入计算。
- 旧二进制文件的可逆保存不代表其语义已解析。具体边界沿用 [明文导出说明](plaintext-database-export.md)，不把数据覆盖核验视为公式或求解器正确性证明。
