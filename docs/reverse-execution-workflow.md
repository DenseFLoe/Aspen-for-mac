# 逐文件逆向执行规则

本流程用于开发总纲第 2 步。按 [AGENTS.md](../AGENTS.md) 和[当前状态](reverse-work-status.md)开工。“已完成”指原件通过静态逆向归档验收。[详细规则](reverse-execution-reference.md)按需查阅，以本页为准。

## 子智能体协作

按需分工，提供必要证据和验收要求，各自使用独立输出路径。主智能体核验并统一发布状态。

## 1. 选择文件

现阶段按[静态验收要求](static-acceptance.md)从 GitHub 主干的待验目录选件，并从未通过目录按报告取修复项。下面的分类资料用于核对身份、范围和来源。

从[本机安装统一清单](installed-baseline.md)的“需要逆向”项核对身份和来源，按当前状态接续未完成项。使用台账复用同哈希、同验收范围的已验收成果。已归档的验收、修复或复验以该件登记的原件 SHA-256 为准。

新件优先读取本机已安装的文件并核对实际路径、产品、安装版本和完整 SHA-256。安装介质用于来源或版本核对，以及补取已确认属于本机目标范围的原件；记录包内成员、用途和指纹。已安装文件与包内文件哈希不同，分开登记。身份或原件仍无法确定时登记阻塞。

开工时确定目标和验收方法，新增信息直接记入台账或同名说明。每件仍按第 3 节核对代码、成员、相关资源和布局的覆盖。

## 2. 孤立或连锁逆向

先处理当前文件。只有证据表明某个范围内文件直接影响本件验收时才追查，缺口和证据位置写入同名说明。证据足够或缺少可推进的条件时结束追查。漏列文件按项目分类规则补证据，连锁处理的文件各自验收。

## 3. 验收并归档

按原件结构核对代码、成员和必要资源的覆盖，托管方法按定义令牌查漏，布局核对控件、事件及绑定。记录工具版本、操作和证据位置。第二套代码对照、重复验证布局和深入外部依赖只用于解决具体验收缺口。影响整件完整性的缺口未解决时，保持未完成。行为测试留到 Windows 重建及对照验收，待验证项记在说明中。各格式按[验收标准](reverse-execution-reference.md#31-完成判定)执行。

整件通过后放入新归档的 `01-completed/`，局部、失败或待验收成果放 `02-incomplete/`。保留产品、原路径和原文件全名，异版本或哈希分开。托管整件用 `<原全名>.cs`，局部用 `<原全名>.序号.cs`，其他格式见[归档细则](reverse-execution-reference.md#32-两类目录和名称)。每份成果配同目录同名 `.md`，记录来源、版本与哈希、范围、状态、验收证据、成果指纹、缺口及下一步。新归档只留成果、说明和必要证据，已有证据直接引用。

## 4. 未完成项

有新输入、方法或证据能推进核实时再重试。否则暂存，在同名说明中记录原因、已尝试的办法和恢复条件。

## 5. 更新清单与下轮入口

归档时核对本轮成果、说明和指纹，通过后在[完成台账](reverse-execution-reference.md#51-完成状态独立记录)标为已完成。按哈希和验收范围同步统一清单对应的完成状态视图，只核对本轮变更的来源行、状态和计数。历史分类快照保留，物理路径数与去重内容数分别统计。

在[当前状态](reverse-work-status.md)记录本轮结果、归档和清单入口及下一步。新增的 `01-completed/` 成果、同名说明和核验证据按产品和原相对路径归档到主干的[静态验收通过目录](../逆向成果/静态验收通过/)，在 [`reverse/01-completed/<轮次>/`](../reverse/01-completed/README.md) 建立轮次索引。按[项目指令](../AGENTS.md#仓库工作流)发布完整交付，并对照本轮台账和成果清单核对 SHA-256。通过已认证的 GitHub 连接器提交到 `codex/` 工作分支，经 PR 合入后回读主干目录和总表。

主干目录内的现有成果按[静态验收要求](static-acceptance.md)验收、修复和复验。按件更新分类目录、总表和相关索引，回读主干确认成果后清理本次生成且已核验的本地副本。逐件历史归档可作为核验依据。
