# 逐文件逆向执行规则

本流程用于开发总纲第 2 步。按 [AGENTS.md](../AGENTS.md) 和[当前状态](reverse-work-status.md)开工。“已完成”指原件通过静态逆向归档验收。[详细规则](reverse-execution-reference.md)按需查阅，以本页为准。

## 子智能体协作

按需分工，提供必要证据和验收要求，各自使用独立输出路径。主智能体核验并统一发布状态。

## 1. 选择文件

从 [Plus](aspen-plus-classification.md) 或 [Properties](aspen-properties-classification.md) 的“需要逆向”清单选择未完成项，优先接续处理中项。结合[共用索引](plus-properties-shared-files.md)和台账复用同哈希、同验收范围的已验收成果。

优先用原版安装包，已安装文件补缺。直接复用已核实的来源清单、包内文件的 SHA-256 和已有提取件，保留各来源的路径、包内成员、产品及版本记录。每轮只计算实际用于逆向的 DLL 的 SHA-256，与对应包内文件的已核实指纹比对。只有安装包换版、来源记录缺失或哈希不一致时，才回查对应安装包。身份或原件仍无法确定时登记阻塞。

开工时确定目标和验收方法，新增信息直接记入台账或同名说明。每件仍按第 3 节核对代码、成员、相关资源和布局的覆盖。

## 2. 孤立或连锁逆向

先处理当前文件。只有证据表明某个范围内文件直接影响本件验收时才追查，缺口和证据位置写入同名说明。证据足够或缺少可推进的条件时结束追查。漏列文件按项目分类规则补证据，连锁处理的文件各自验收。

## 3. 验收并归档

按原件结构核对代码、成员和必要资源的覆盖，托管方法按定义令牌查漏，布局核对控件、事件及绑定。记录工具版本、操作和证据位置。第二套代码对照、重复验证布局和深入外部依赖只用于解决具体验收缺口。影响整件完整性的缺口未解决时，保持未完成。行为测试留到 Windows 重建及对照验收，待验证项记在说明中。各格式按[验收标准](reverse-execution-reference.md#31-完成判定)执行。

整件通过后放入新归档的 `01-completed/`，局部、失败或待验收成果放 `02-incomplete/`。保留产品、原路径和原文件全名，异版本或哈希分开。托管整件用 `<原全名>.cs`，局部用 `<原全名>.序号.cs`，其他格式见[归档细则](reverse-execution-reference.md#32-两类目录和名称)。每份成果配同目录同名 `.md`，记录来源、版本与哈希、范围、状态、验收证据、成果指纹、缺口及下一步。新归档只留成果、说明和必要证据，已有证据直接引用。

## 4. 未完成项

有新输入、方法或证据能推进核实时再重试。否则暂存，在同名说明中记录原因、已尝试的办法和恢复条件。

## 5. 更新清单与下轮入口

归档时核对本轮成果、说明和指纹，通过后在[完成台账](reverse-execution-reference.md#51-完成状态独立记录)标为已完成。按哈希和验收范围同步各产品总清单、适用重复子清单和共用索引的新状态视图，只核对本轮变更的来源行、状态和计数。原分类与旧快照保留，来源数与去重内容数分别统计。

在[当前状态](reverse-work-status.md)记录本轮结果、归档和清单入口及下一步。每轮将新增的 `01-completed/` 成果、同名说明和可上传的验收证据复制到 [`reverse/01-completed/<轮次>/`](../reverse/01-completed/README.md)，保留产品、原相对路径及文件名。对照本轮台账的“已完成”状态和 `artifacts.csv` 核对成果及说明的 SHA-256。混合归档提取可上传文件并另记来源和指纹，原版二进制及其编码副本留在本机。更新已完成目录入口，和本轮文档及状态清单一起提交到工作分支并上传公开仓库。`02-incomplete/` 完整成果留在本机。

每轮逆向开发结束后，只要“需要逆向”清单还有未完成项，就在 Codex 的 Aspen 项目文件夹下新建一个聊天并发送 `继续逆向开发`，直到清单中的所有项目通过本阶段验收才停止新建聊天。

## 一次性衔接：既有成果

首轮已将旧成果的处置记入台账。后续按当前台账接续，有具体缺口时只复核相关旧成果。见[首轮历史交接记录](../inventories/reverse/20261119-01/README.md#历史交接)。
