# 逐文件逆向执行规则

制定日期：2026-11-19（北京时间）。本规则落实用户提出的五项安排，适用于 Aspen Plus、Aspen Properties 及有归属证据的共享组件；Properties 配套数据库服务器继续单列。其他产品自身文件沿用范围外处理。

本规则是[开发总纲第 2 步](development-requirements.md#2-逐个反编译并按原名归档)的执行细则。下文第 1 项是接下来每轮工作的起点，开发总纲原有的盘点、逐文件归档、Windows 重建和 Mac 适配顺序保持。当前阶段的“逆向完成”指原版逐文件反编译与归档通过验收，后续编译、运行和行为一致性另行验收。

本次修订只确立执行规则，没有据此将既有文件标为完成。既有成果按文末的一次性衔接规则逐项处理。

## 子智能体协作

2026-11-19 用户授权：本规则适用的逐文件逆向任务均允许按需调用子智能体，包括既有成果复核、清单比对、孤立或连锁逆向、依赖分析、验收复核、归档说明和完成状态整理。模型自主决定是否调用、数量和分工，无需每轮另行征求用户授权。

主智能体统一协调文件身份、依赖关系和处理范围，分派任务时明确输入、输出路径与验收要求，避免重复处理同哈希内容或并行覆盖同一成果。子智能体遵守相同的产品范围、阶段边界、资产保留及仅本地保存要求；主智能体汇总并核验其成果后，统一发布验收结论和清单完成状态。

## 1. 从已有“需要逆向”清单选择文件

1. 从[Properties 当前清单](aspen-properties-classification.md)、[Plus 既有分类](aspen-plus-classification.md)及[共用关联](plus-properties-shared-files.md)中的“需要逆向”项选择一个原版文件作为本轮起点。每轮先读取当前完成状态，再选择未完成的内容；已验收完成的相同内容不重复逆向。
2. 优先使用对应产品原版安装包中的载荷。已安装文件用于补缺、版本差异及运行取证。核对实际读取内容的 SHA-256、版本、产品、原相对路径和包内成员；同名异哈希分别处理，容器和内层代码成员分别确认。
3. 以完整内容 SHA-256 和统一 `analysis_key` 组织分析，保留全部来源记录。已有同哈希成果先核实验收范围和归档完整性，满足本阶段要求即可复用。缺少可读原内容或可靠身份时登记阻塞，不凭名称认定重复或完成。
4. 模型自行决定选择顺序，优先处理能解除当前阻塞的文件、证据与依赖已齐且能形成完整成果的文件，以及可被多处复用的内容。暂存项只有满足恢复条件或取得新证据后才重新进入处理队列。
5. 开始前建立本轮记录：轮次、清单来源与指纹、起点文件身份、已有成果、目标范围、验收方法、待补证据及新输出目录。记录本轮选择和未优先处理项的主要理由。

“需要逆向”是处理路线，不因逆向完成而改为“不需要逆向”。原分类状态与本阶段完成状态分别维护。

## 2. 判断孤立逆向或连锁逆向

模型根据文件实际情况自行决定孤立处理或关联处理，不要求用户逐次批准。下列依据用于判断是否加入关联文件，并逐项留痕：

| 情况 | 处理方式 |
| --- | --- |
| 当前文件的实现及边界可独立核对，外部接口已有足够证据 | 孤立逆向，记录外部依赖即可 |
| 缺少被调用实现、共享结构、资源绑定、动态加载目标或数据约定，直接阻碍当前文件验收 | 有调用、引用、安装归属或运行证据时，将必要的关联文件加入本轮 |
| 关联内容已有同哈希且符合本阶段验收的成果 | 引用既有成果并核对接口，不重复逆向 |
| 仅同目录、同名或存在一般引用，尚不能证明需要深入 | 先登记关联，不自动扩展 |

每加入一个文件，记录从哪个文件引出、证据位置、要解除的具体缺口、预期产出及停止条件。新增目标仍须属于本项目范围并有“需要逆向”的分类依据；必要的配置、资源、数据库按自身格式辅助核对，不因此改成代码反编译对象。发现范围内但未入清单的程序，先补来源与分类证据，再登记新项；Plus 冻结分类的修改另行记录，不在本轮静默重分类。

**继续连锁的标准：** 新节点有直接证据、属于范围内，并且其结果能解除当前验收缺口或形成必要的完整模块；工具和输入允许取得可核对的进展。继续前重新判断以上条件，而非沿全部依赖递归展开。

**停止连锁的条件：** 当前目标已可验收；剩余依赖的接口证据已足够；遇到已处理节点或循环依赖；缺少原内容、工具或必要的运行证据；连续尝试没有新增有效证据；下一节点属于范围外。停止时保存已取得的成果、未解边及恢复条件。循环依赖可作为一组分析，但每份原版文件仍分别验收。

开始时记录本轮可交付的边界；确需扩展时写明理由与新的边界。不得以“尚有依赖”为由无限延长本轮，也不得因链中一份文件完成而把整条链标为完成。

## 3. 验收、命名和归档

用户安排中的“第二轮结束后”统一解释为“本轮第 2 项逆向工作结束后”。孤立处理可结束后归档；连锁处理可边做边归档或结束后统一归档，由模型根据成果稳定程度决定。处理中保留检查点，每轮结束前完成归档和清单同步。

### 3.1 完成判定

一份原版文件只有同时满足以下要求，才能标注“逆向完成”：

- **来源确定：** 有原版产品、来源路径、版本或不可取得原因、完整内容 SHA-256，以及与清单项的对应关系。
- **覆盖完整：** 按原文件结构核对本阶段应恢复的代码、成员和相关资源，有预期项与输出项的覆盖记录。托管程序集核对类型及方法实现；原生文件核对代码区域、函数、入口及必要的数据引用。原生伪代码和反汇编只是成果形式，不能仅凭导出这些内容认定完整。
- **缺口已处理：** 没有未解释的缺失方法体、反编译失败、占位实现、关键类型无法推断或未解析的内部代码成员。原版自身的抽象、接口或外部声明应由原版证据说明，不误当作恢复失败。只恢复局部类型或函数时，原文件保持未完成。
- **证据可复查：** 记录工具与版本、执行方式、日志、结构与实现核对证据、依赖边界，以及静态结论、原版运行观察和推断之间的区别。影响完整性判断的未核实推断必须先解决。
- **归档完整：** 输出实际存在于本轮 `01-completed/`，名称和路径正确，所有成果都有同目录同名 `.md`，输出指纹及验收记录可核对。

验收方法按文件格式在处理前确定。工具运行成功、没有报错、生成了整份 `.cs`、通过编译或已经位于“已完成”目录，都不能单独替代上述判定。本阶段不要求取得原开发者的逐字源码，也不以依赖文件全部逆向完成作为普遍前提；外部依赖边界须足以支撑本文件的验收。

### 3.2 两类目录和名称

沿用[每轮成果分类与逐文件说明](development-requirements.md#11-每轮成果分类与逐文件说明)：

- `01-completed/`：完整通过本阶段验收的成果。
- `02-incomplete/`：局部恢复、失败、阻塞、暂存或尚待验收的成果。处理中的输出在最终验收前不得用于发布完成状态。

本轮使用新归档路径，在两类目录下保留产品、原相对路径及原文件全名。同路径异版本或异哈希使用独立版本/哈希目录，原版输入与历次成果均不覆盖。沿用现成两类目录的组织规则，不为相同状态再建立含义不明的“逆向完成”第三类目录。

整份托管代码完成件命名为 `<原文件全名>.cs`；局部输出为 `<原文件全名>.<序号>.cs`。例如 `A.dll.cs` 配 `A.dll.md`，`A.dll.01.cs` 配 `A.dll.01.md`。原生、IL、VBA 和资源材料保留原文件全名及能说明格式的后缀，不将伪代码伪装成托管源码；每份成果仍有独立同名说明。名称、原成员身份和输出路径在索引中一一对应。

逐文件说明除既有来源、范围、完成状态、验收依据、缺口和下一步要求外，还记录本轮关联决策、成果 SHA-256，以及未完成项的重试或暂存决定。目录汇总不能替代逐文件说明。

## 4. 未完成项的重试或暂存

本阶段先判断是否**重新反编译、调整工具或补充分析**。用户原文的“立刻重新编译”不作为自动进入 Windows 工程重建的指令；Windows 源码重建、应用构建和行为验收仍按开发总纲第 3 步执行。

| 决定 | 判断标准 | 必须记录 |
| --- | --- | --- |
| 立即继续或重新反编译 | 失败原因明确，存在可执行的改进，如补齐已有依赖、调整参数、改用适用工具；预计能解除本轮缺口 | 失败证据、具体改进、验收方法及本次结果 |
| 优先补齐关联文件 | 缺口由已证实的范围内依赖造成，补齐后能推进本轮验收 | 依赖关系、链的边界和回到原文件的条件 |
| 暂存 | 需要尚未取得的输入、格式知识、工具或运行证据；继续扩展会越界；相同办法已无新进展 | 阻塞原因、已尝试方法、保留成果、下一步和可检查的恢复条件 |

重试必须有新的输入、方法或证据；同一失败条件下不机械重复。是否立即继续由模型自行判断并说明理由，不设与所有文件共用的盲目重试次数。暂存仍属未完成，不记为成功或从待办中消失。

## 5. 清单同步和下轮选择

### 5.1 完成状态独立记录

为当前工作清单维护独立的完成状态台账，再关联生成带状态的“需要逆向”清单视图。不得把 `classification_status`、分类复核字段或空的 `review` 当作逆向完成状态。固定使用以下本阶段状态：

| 状态 | 含义及调度 |
| --- | --- |
| 未开始 | 可选择 |
| 处理中 | 优先恢复该轮，避免重复启动同一内容 |
| 未完成 | 已处理但未通过验收，可根据缺口继续 |
| 暂存 | 保留缺口，恢复条件满足后再选 |
| 已完成 | 已通过验收且成果、说明和证据均已归档；下轮跳过相同内容 |
| 待复核 | 旧完成记录证据不足，或后来发现实质缺口；不能作为完成结果复用 |

台账至少包括：原内容 SHA-256、`analysis_key`、来源记录身份、产品及版本、原路径/包内成员、阶段、状态、轮次、归档与说明路径、成果指纹、验收记录、未完成原因、恢复条件及状态变更依据。缺少稳定 `record_id` 的旧清单用来源字段组合关联，不能只匹配文件名。

### 5.2 先归档，再发布完成标记

1. 核对原内容身份，完成逐文件验收，写齐成果及说明。
2. 在新归档中核对文件存在、路径、指纹和证据，再记录台账的“已完成”。尚未写入或核验的输出保持未完成状态。
3. 根据同哈希及同验收范围同步全部相关来源：对应产品“需要逆向”总清单、适用的重复子清单及共用索引；同属 Plus 与 Properties 时三方视图同时引用同一成果。保留全部来源行，不重复计为多个独立完成内容。
4. 核对视图与台账一致，记录本轮已完成、未完成、暂存及剩余项，并更新当前入口。发布中断时先核对和补齐同步，下轮读取台账与归档，避免重复处理或误报完成。

原本地分类清单、旧轮次证据及 `inventories/2026-11-19/` 已发布快照保持原样。完成标记写入新轮次台账和带状态的新清单视图，Plus 的原分类字段继续冻结。这样既能在“需要逆向”项旁看到“已完成”，又能保留原分类及历史校验。新状态索引使用新路径，记录来源和指纹。完整反编译正文和原版二进制可按[仓库工作流](../AGENTS.md#仓库工作流)公开发布。数据库及公式仅本地保存。

下轮只跳过本阶段已验收完成、原哈希匹配且归档可核验的内容。发现新版本、新哈希、归档缺失或实质恢复缺口时，建立新项或记为待复核并记录原因，不沿用无效完成结论。来源记录数和去重内容完成数分别统计；局部源码条数不能代替原文件完成数。

## 一次性衔接：既有已完成和未完成成果

此节只用于消化规则生效前已有的成果，不取代后续每轮流程。

1. 首次按本规则执行逆向前，基于[既有归档入口](step-2-source-attribution.md#当前源码归档)及已登记补充归档，冻结一份有限的历史待复核表，记录每份原内容、既有输出和证据位置。旧索引中的 4 份已完成、35 份未完成是历史快照，不能直接视为新规则验收结果。仅核查范围内的 Plus、Properties 及相关共享文件；范围外成果继续保留，不启动其逆向。
2. 对原“已完成”项核对原哈希、完整覆盖、已知警告、逐文件说明和归档指纹。证据充分的无需重复反编译；在新路径补齐本规则要求的说明及验收记录、完成归档核验后，直接执行第 5 项清单同步。发现缺口时，在新记录中转为未完成或待复核，保留旧快照。
3. 对原“未完成”项逐项依第 4 项判断优先补齐还是暂存，记录原因和恢复条件。能解除本轮阻塞且具备可执行办法的优先；单纯存在于旧目录中不构成必须立即完成的理由。
4. 每项完成历史复核及相应归档、状态同步或暂存交接后，在衔接表标明处理结果，该项不再重复适用此临时规则。暂存项交回常规队列，后续按恢复条件处理。
5. 全部历史项均有明确处置、范围内状态同步一致后，本节失效，可从现行规则中移除，并在完成记录中保留衔接表和证据位置。失效不构成删除或覆盖原资料、历史输出或受保护资产的授权。

每轮最终交付应能回答：选了哪个原文件、为什么连锁或停止、哪些内容通过何种验收、成果与逐文件说明在哪里、哪些缺口暂存、哪些清单状态已同步。项目开发文档和状态元数据按仓库流程提交；完整本地研究资料继续保留。
