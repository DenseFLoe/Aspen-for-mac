# 四组静态验收与 Issue 协作修复

Aspen Plus 和独立 Aspen Properties 各按原件开展静态验收。四个验收聊天各领一份待验清单。静态验收修复组从未通过清单中选件，在原仓库开 Issue 请协作者修复。原 Aspen 项目中的长期监视聊天跟踪这些 Issue，复验协作者提交的文件。各组主模型可以按需调用子智能体，自行选择模型与推理档位，复核证据并负责提交。

分工依据为 `b0f60b63ce99837ea3a8cf77e19e351b7b72047d` 的[逐件总表](../../逆向成果/逐件总表.csv)，该版的总表 blob 为 `6a37f2f723df51f4a6f340387fefbe9b17c23f1f`。初次将 961 个待验原件按 SHA-256 升序轮流分给一至四组，另列 285 个未通过件。63 个已通过件及 85 个“未成功”件不在初始队列内。`repair.csv` 的“复验组”沿用既有清单字段，Issue 交付统一由长期聊天复验。

## 每件怎么处理

| 谁来处理 | 查证结果 | 同一次提交完成的操作 |
| --- | --- | --- |
| 验收一至四组 | 静态通过 | 将整个原件目录从 `逆向成果/待静态验收/` 移到 `逆向成果/静态验收通过/`，写入逐件证据，从本组清单移除。 |
| 验收一至四组 | 静态未通过 | 将整个原件目录移到 `逆向成果/静态验收未通过/`，写清缺口和复现依据，从本组清单移入 `repair.csv`，保留原清单字段。 |
| 长期监视聊天 | 协作者交付通过复验 | 将核验过的修改、逐件证据和 Issue 引用归档，直接把整个原件目录移到 `逆向成果/静态验收通过/`，从 `repair.csv` 移除。 |
| 长期监视聊天 | 协作者交付仍未通过，或证据不足 | 保留未通过状态，在同一个 Issue 留下复验结论、对应提交 SHA 和待补项，等待新提交或证据。 |

每次移动都保留产品、对象目录相对路径、历史报告和既有文件。更新对象 README 的当前判定和证据入口、逐件总表的状态与目录、成果首页的计数，以及受这次移动影响的现行索引和链接。按[逐文件验收标准](../../docs/reverse-execution-reference.md#31-完成判定)核对原件身份、可编辑源码、成员与资源覆盖，记录可重查的差异。哈希用来确认拿到哪一件，工具退出成功或编译成功只证明对应步骤完成。环境故障、原件暂时无法读取时保留待办，记明阻塞条件，继续本组其他可处理件。

## 开 Issue 并请协作者修复

1. 从主线 `repair.csv` 选取有明确问题、错误报告和可定位原件的部分文件。开单前按原件 SHA-256 查询仓库现有 Issue。同一个原件有多个相关缺口时汇总到同一 Issue。选件、发单和等待协作者期间，原件留在未通过目录和修复清单。
2. 在 [DenseFLoe/Aspen-for-mac 的 Issues](https://github.com/DenseFLoe/Aspen-for-mac/issues) 开单。标题用 `[静态验收修复] <原文件名>`，正文放原件信息、错误成果、错误报告和复验要求。通知本项目协作者，并请其在 Issue 回贴对应 PR 或固定提交及修改文件路径。
   - **错误的逆向成果**。提供实际文件或固定提交的下载链接，标明原路径和 Git blob SHA。
   - **被逆向原文件**。提供实际原文件或固定提交的下载链接，并列明产品版本、安装包成员或原相对路径及 SHA-256。通过仓库提供下载时，可以将文件放在 `codex/` 工作分支的 `issue-materials/<Issue 号>/`，回读验证后将固定提交的下载链接贴入 Issue。其他受保护资产按 [AGENTS.md](../../AGENTS.md#仓库工作流) 保存。
   - **错误报告**。给出已核实的差异、定位、复现步骤和本件通过判据，可直接写在 Issue 或附仓库中可公开的报告固定链接。

## 持续监视和复验

1. 长期聊天定期检查修复 Issue、评论及关联 PR 或提交，包括已关闭 Issue 中尚未复验的交付。用 Issue 号、原件 SHA-256、交付提交 SHA 和文件路径对应同一件，并记录最近一次结论。
2. 发现新交付时读取固定提交和文件差异，从本机核对原件指纹，重做原失败检查，并按整件标准核对受影响的代码、成员和资源。用原件和实际修改文件作依据。相同版本已有结论时复用，交付 SHA 变化时复核变化。缺少可读文件或证据时在该 Issue 记录所缺项。
3. 通过后按下节合入修改与验收记录，回读主线，回贴通过证据和合入提交，再关闭 Issue。若协作者提交已合入，按同样标准复验其固定提交，另补验收和台账变更。复验仍有缺口时在原 Issue 回报可定位的差异。
4. 修复组的开单、跟踪与复验由同一个长期聊天持续进行。无新交付时等待下一次检查。

## 分支、清单与合入

1. 五份活动清单以 GitHub `main` 已合入的版本为准。开工、提交前各读取一次最新主线与本分支，按原件 SHA-256 检查当前状态和唯一归属。每组只有一个活动主聊天。子智能体只在明确分出的原件和独立临时目录工作。
2. 在本组工作分支准备本轮增量。清单、总表和计数按本轮原件逐行更新，保持 CSV 原有列、顺序约定与编码。清单按原件 SHA-256 排序。目录移动、证据与台账用同一次提交发布，使接班人读到一致的状态。文件已在远端的部分复用原 Git 树或 blob；仅发布项目允许公开的内容。
3. 提交前在候选快照运行 `python tools/check_static_queues.py <快照根目录>`，再核对本轮新旧路径、对象数、文件指纹及验收证据。工作分支通过 PR 合入主线，核对 PR 头和合并后的有关记录。遇上其他组刚合入的改动，从最新主线逐件重放仍适用的增量，保留别组更新，重新核验。重复运行时，已发布且指纹一致的转移直接跳过。若遇到必须满足的分支检查，保留工作提交并跟进。

## 每轮收尾、清理和接班

- 按件按需读取原件与成果，优先复用现有只读输入。核验清单只需逐件总表与五份 CSV，可在小型临时快照运行。每份接班指令继续授予该聊天主模型使用子智能体并自主选择模型、推理档位的权限。
- 本轮临时下载、解压、分析缓存和构建中间物放在 `.local/static-review/<组>/<轮次>/scratch/`。待发布成果独立暂存，交接只留原件 SHA-256、分支和提交、证据位置、余项及必要复现说明。分支与本地目录一一对应，组名使用 `audit-1` 至 `audit-4` 或 `repair`。
- 成功验收的可公开成果以 GitHub 对应成功目录为保存位置。先从已合入的提交回读目标目录的完整清单及 Git blob 指纹，同新建或修订文件本地指纹比对，确认原目录已移走、队列归属正确，然后删除本轮生成的本地成果副本。远端提交失败时保留唯一待交付副本，恢复后核验再清。含凭据及其他限定仅本地保存的材料继续按原资产规则管理，公开记录只引用允许发布的证据。
- 每轮结束，包括未通过或阻塞的轮次，都清掉已无用的本轮临时文件。可运行 `tools/clear_static_scratch.ps1 -Lane audit-1 -Round <轮次>` 清本组本轮的暂存目录；先确认其中没有唯一待交付或复现材料。历史原件、永久保留的数据库及公式资产、其他组工作目录保持保留。两组共同使用的工具和只读输入不要混入本轮临时目录。
- 验收一至四组的本轮主聊天负责在原 Aspen 项目创建**一个**本组接班聊天并发送开工指令，写明同一组、分支、已合入提交或待合入 PR、手中原件、待做事项和清理结果。创建前核实本组接班聊天是否已存在，创建成功后本轮停止领件。若创建返回不确定，先查已有聊天并复用。按实际队列和新证据连续接力。队列暂空或仅余已记录且条件未变的阻塞件时，在交接中标明等待条件。
