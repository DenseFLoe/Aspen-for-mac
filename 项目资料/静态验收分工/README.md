## 每件怎么处理

| 谁来处理 | 查证结果 | 同一次提交完成的操作 |
| --- | --- | --- |
| 验收一至四组 | 静态通过 | 将整个原件目录从 `逆向成果/待静态验收/` 移到 `逆向成果/静态验收通过/`，写入逐件证据，从本组清单移除。 |
| 验收一至四组 | 静态未通过 | 将整个原件目录移到 `逆向成果/静态验收未通过/`，写清缺口和复现依据，从本组清单移入修复清单，保留复验组。 |
| 失败修复组 | 已查明并修好 | 将整个原件目录由 `静态验收未通过/` 移回 `待静态验收/`，记录改动与证据，从修复清单移除，只加入“复验组”列指定的那一份清单，由该组重新验收。 |
| 失败修复组 | 本次仍修不好 | 维持目录、原件状态和所有清单原样。在本组交接记录注明尝试过的办法、剩余问题和何时值得再试。 |

每次移动都保留产品、对象目录相对路径、历史报告和既有文件。更新对象 README 的当前判定和证据入口、逐件总表的状态与目录、成果首页的计数，以及受这次移动影响的现行索引和链接。按[逐文件验收标准](../../docs/reverse-execution-reference.md#31-完成判定)核对原件身份、可编辑源码、成员与资源覆盖，记录可重查的差异。哈希用来确认拿到哪一件，工具退出成功或编译成功只证明对应步骤完成。环境故障、原件暂时无法读取时保留待办，记明阻塞条件，继续本组其他可处理件。

## 五个分支如何交接

1. 五份活动清单以 GitHub `main` 已合入的版本为准。开工、提交前各读取一次最新主线与本分支，按原件 SHA-256 检查当前状态和唯一归属。每组只有一个活动主聊天；子智能体只在明确分出的原件和独立临时目录工作。
2. 在本组工作分支准备本轮增量。清单、总表和计数按本轮原件逐行更新，保持 CSV 原有列、顺序约定与编码。清单按原件 SHA-256 排序。目录移动、证据与台账用同一次提交发布，使接班人读到一致的状态。文件已在远端的部分复用原 Git 树或 blob；仅发布项目允许公开的内容。
3. 提交前在候选快照运行 `python tools/check_static_queues.py <快照根目录>`，再核对本轮新旧路径、对象数、文件指纹及验收证据。工作分支通过 PR 合入主线，核对 PR 头和合并后的有关记录。遇上其他组刚合入的改动，从最新主线逐件重放仍适用的增量，保留别组更新，重新核验；重复运行时，已发布且指纹一致的转移直接跳过。若遇到必须满足的分支检查，保留工作提交并跟进。下一组在主线回读成功后接件。

## 每轮收尾、清理和接班

- 按件按需读取原件与成果，优先复用现有只读输入。核验清单只需逐件总表与五份 CSV，可在小型临时快照运行。每份接班指令继续授予该聊天主模型使用子智能体并自主选择模型、推理档位的权限。
- 本轮临时下载、解压、分析缓存和构建中间物放在 `.local/static-review/<组>/<轮次>/scratch/`。待发布成果独立暂存，交接只留原件 SHA-256、分支和提交、证据位置、余项及必要复现说明。分支与本地目录一一对应，组名使用 `audit-1` 至 `audit-4` 或 `repair`。
- 成功验收的可公开成果以 GitHub 对应成功目录为保存位置；成功修复的可公开成果以 GitHub 待验目录为保存位置。先从已合入的提交回读目标目录的完整清单及 Git blob 指纹，同新建或修订文件本地指纹比对，确认原目录已移走、队列归属正确，然后删除本轮生成的本地成果副本。远端提交失败时保留唯一待交付副本，恢复后核验再清。含凭据及其他限定仅本地保存的材料继续按原资产规则管理，公开交接只记录允许发布的证据。
- 每轮结束，包括未通过或阻塞的轮次，都清掉已无用的本轮临时文件。可运行 `tools/clear_static_scratch.ps1 -Lane audit-1 -Round <轮次>` 清本组本轮的暂存目录；先确认其中没有唯一待交付或复现材料。历史原件、永久保留的数据库及公式资产、其他组工作目录保持保留。两组共同使用的工具和只读输入不要混入本轮临时目录。
- 本轮主聊天负责在原 Aspen 项目创建**一个**本组接班聊天并发送开工指令，写明同一组、分支、已合入提交或待合入 PR、手中原件、待做事项和清理结果。创建前核实本组接班聊天是否已存在，创建成功后本轮停止领件。若创建返回不确定，先查已有聊天并复用。按实际队列和新证据连续接力。队列暂空或仅余已记录且条件未变的阻塞件时，在交接中标明等待条件。任何组交入新件时检查接收组，有活动聊天即由其接收，休眠时在原项目恢复该组唯一聊天。五组全部无可推进项时报告剩余阻塞或完成情况。
